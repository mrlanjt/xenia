# Xenia 项目理解与「新项目支持 macOS Apple Silicon（M1/M2/M3/M4）」可行性分析

> 结论先行：
> - **在“不改造现有代码”前提下，直接让当前仓库跑在 macOS ARM 并达到可用状态，基本不可行**。
> - 但以本项目为“架构与实现参考”，**新起一个兼容性导向项目**是可行的。
> - 建议采用「分阶段交付 + 先验证关键技术路径」方式，先做最小可运行版本（PoC），再决定是否投入完整产品化。

---

## 1. 我对当前项目的理解（从代码与构建系统角度）

### 1.1 平台与构建现状

- 官方构建文档明确写到：
  - Windows 为主；
  - Linux 支持“**极其实验性且不完整**”；
  - 没有提供 macOS 的正式构建说明。
- 根目录 `premake5.lua` 虽然有 `macosx` 分支，但把 Mac 架构硬编码成 `x86_64`，并设置了 Xcode `ARCHS = x86_64`，**没有 Apple Silicon 原生目标**。

### 1.2 CPU 后端现状

- 仓库主工程在 app 层仅在 `architecture:x86_64` 时链接 `xenia-cpu-backend-x64`。
- `Emulator::Setup` 里创建 CPU 后端时也主要在 `XE_ARCH_AMD64` 条件下启用 x64 JIT 后端。
- 这意味着当前路径强依赖 x64 主机后端，Apple Silicon（ARM64）即便能编过部分模块，也会卡在 CPU 执行核心能力上。

### 1.3 图形与系统依赖现状

- 工程里存在 Windows 专属 D3D12 路径，也有 Vulkan 路径；
- Linux/Android 有一些平台代码与依赖处理，但 macOS 缺少完整一等公民路径；
- 另外，POSIX 路径中可见 Android/Linux 专属接口分支，说明跨平台抽象虽有基础，但离“macOS ARM 可运行”仍有明显工程鸿沟。

## 2. 针对你的三点诉求逐条分析

## 2.1 诉求1：支持 mac ARM（M1/M2/M3/M4）

### 可行性判断

- **可行（前提：新项目）**。
- 不建议目标是“一步到位完整兼容全部游戏”，而是先定义技术可行目标：
  1. 可启动、可加载最小样例；
  2. 可执行核心 CPU 指令子集；
  3. 可完成基础图形输出路径（例如 Vulkan/Metal 中的一条）；
  4. 可进行性能与正确性基准评估。

### 技术路线建议（新项目）

- **CPU 层**：
  - 方案A：解释器优先（先正确性，后性能）；
  - 方案B：ARM64 JIT 后端（性能更好，但研发成本高）；
  - 推荐：A 起步，B 并行预研。
- **GPU 层**：
  - 路线1：Vulkan（通过 MoltenVK 落到 Metal）；
  - 路线2：直接 Metal 后端。
  - 推荐：先 Vulkan+MoltenVK 快速验证，再评估是否投资原生 Metal。
- **系统层**：
  - 文件系统、线程、异常、内存映射都做清晰平台抽象；
  - 避免写死 Linux/Windows 特性。

## 2.2 诉求2：代码无法改造，可参考这个项目，起一个新项目

### 可行性判断

- **完全可行**，而且从风险控制上是更优策略。
- 原因：当前项目历史包袱较重、核心路径偏向既有架构；直接“无改造接入”几乎等于外部套壳，收益低、成本高。

### 新项目建议边界

- 仅参考：
  - 模块边界划分（CPU/GPU/HID/Kernel/VFS）；
  - 调试工具链思路；
  - 一些协议/格式处理思路。
- 不直接复用：
  - 与 x64 强耦合的 JIT 执行路径；
  - 与特定平台深绑定的图形/窗口代码。

### 具体落地方式（可执行）

1. **项目初始化（第 1 周）**
   - 建立新仓库（独立 license、独立 CI、独立 issue 模板）；
   - 建立目录骨架：`core/ cpu/ gpu/ platform/ tools/ tests/`；
   - 先做 macOS ARM64 的 build target（CMake + clang）。

2. **核心闭环（第 2~4 周）**
   - CPU：实现最小解释器，只覆盖必要指令子集；
   - GPU：先打通 Vulkan + MoltenVK 的最小渲染路径；
   - 平台：窗口、输入、文件系统、日志打通。

3. **验证闭环（第 5~8 周）**
   - 构建「开发者研究」样本集（10~20 个 case）；
   - 接入自动化回归（启动、渲染、崩溃、性能采样）；
   - 输出第一版兼容性报告（可运行 / 不可运行 / 原因）。

4. **迭代闭环（第 9~12 周）**
   - 修核心正确性问题（优先 crash 和严重图形错误）；
   - 补关键性能路径（内存、同步、shader cache）；
   - 评估是否进入 ARM64 JIT 研发阶段。

### 建议里程碑（可做立项门槛）

1. **M0（2~4周）**：
   - 工程骨架 + CI（macOS arm64）+ 基础日志与配置系统。
2. **M1（4~8周）**：
   - CPU 解释器最小闭环，可跑指令单测。
3. **M2（4~8周）**：
   - 图形最小输出（黑屏到首帧）。
4. **M3（6~12周）**：
   - 关键性能路径优化、兼容性样本集跑通。
5. **M4（持续）**：
   - ARM64 JIT / Metal 深化 / 兼容数据库建设。

## 2.3 诉求3：补充其他支撑信息，用于判断项目是否值得做

建议把立项判断拆成以下 5 个维度，每个维度都给“可量化门槛”。

### A. 技术可行性门槛

- 是否能在 8~12 周内拿到 PoC：
  - 能启动；
  - 能执行核心指令子集；
  - 能输出基础画面；
  - 能稳定跑 10~30 分钟不中断。

### B. 性能可达性门槛

- 在 M1/M2 基础机型上：
  - CPU 占用、帧时间、内存峰值是否在预设阈值内；
  - 是否有明确可优化路径（不是“只能靠硬件堆”）。

### C. 法务与合规门槛

- 许可证合规（当前参考项目为 BSD 协议）；
- BIOS/固件/密钥/游戏数据处理边界清晰；
- 发布地区与分发平台的政策风险评估完整。

### D. 工程投入与团队门槛（按你的要求改为最小团队）

- **最小团队建议：1 人 + Codex + 其他 AI 工具**。
- 分工建议：
  - 人：架构决策、关键技术取舍、验收标准、风险管理；
  - Codex：脚手架生成、批量重构、测试样例生成、文档同步；
  - 其他 AI：性能分析建议、日志聚类、崩溃归因辅助。
- 适用边界：
  - 适合“开发者研究”项目；
  - 不适合立即承诺商用品质与大规模兼容库。

### E. 用户价值与业务门槛（按你的要求明确）

- **目标用户：开发者研究（Developer Research）**。
- 成功指标（研究导向）：
  - 可复现实验数量（样本可重复运行）；
  - 调试可见性（日志、追踪、崩溃定位速度）；
  - 关键子系统覆盖率（CPU/GPU/内存路径）；
  - 每周可稳定关闭的问题数（burn-down）。

---

## 3. 风险清单（按优先级）

1. **CPU 执行层风险最高**：ARM64 JIT 难度与正确性验证成本大。
2. **GPU 语义映射风险高**：主机图形 API 与客体 GPU 行为差异复杂。
3. **兼容性长尾风险高**：不同游戏触发不同边界行为。
4. **性能优化周期不可低估**：PoC 能跑 ≠ 可用。
5. **测试资产不足风险**：没有自动化兼容集会拖慢迭代。

## 4. 实施清单（你现在就可以开始）

### 第 0 天（今天）
- 定义目标：只做“开发者研究”PoC，不承诺完整兼容。
- 定义样本：挑 10 个可公开测试样本作为基准。

### 第 1~3 天
- 初始化仓库与 CI（macOS 14/15 + arm64 runner）。
- 建立 coding standard、issue 模板、性能记录模板。

### 第 4~10 天
- 跑通窗口 + 日志 + 配置 + 文件加载最小链路。
- 建立自动化 smoke test（启动即测、崩溃即报）。

### 第 11~20 天
- 打通 CPU 解释器最小子集（先 correctness）。
- 打通 GPU 最小显示路径（先有画面，再优化）。

### 第 21~30 天
- 输出《PoC 可行性报告》：
  - 已跑通项；
  - 阻塞项；
  - 下一阶段投入与产出评估。

---

## 5. 建议决策（可直接给评审会）

- **建议立项，但按“阶段闸门”推进**，不是一次性承诺完整可用产品。
- 第一阶段只做 PoC，预算与周期受控；
- 满足门槛后再进入第二阶段（功能拓展 + 性能优化 + 兼容性扩展）。

一句话：

> 你的方向是对的：**不要硬改旧项目，应该基于其经验新起项目。**
> 并且在你的资源约束下（1人+Codex+AI），最现实的定位就是“开发者研究型项目”，先以 PoC 闸门推进。
